An AI that runs the game: Storyteller's bid to solve interactive narrative

A new voice-first platform has spent the last twelve months building the infrastructure that other AI storytelling tools have ignored: a rigorously curated knowledge base, verified term by term.

SQ
Storyteller Quarterly · Research & Technology Staff
9 min read
01 — THE PROBLEM
HALLUCINATION AT THE TABLE

Ask any large language model to run a game of Dungeons & Dragons and it will comply with enthusiasm. Ask it to apply the specific rules of a custom tabletop system — one with unique mechanics, a proprietary vocabulary, and a lore built over decades — and the confident tone persists even as the accuracy collapses. The model invents rules that don't exist, conflates mechanics from disparate systems, and serves this confabulation in the same fluent prose as the correct material. For casual play, this is a friction point. For a commercial product, it is a liability.1

Storyteller, a voice-first interactive storytelling platform currently in development, is attempting to solve this problem not by selecting a smarter base model but by solving the data problem upstream. The theory is straightforward: if you can give the AI an authoritative, machine-readable knowledge base of every relevant term, rule, mechanic, and concept — and if you can do that before content reaches users — hallucination in the domain becomes a tractable engineering problem rather than an emergent limitation of the underlying model.

The implementation is where this becomes technically interesting. Storyteller's team has spent the last several months building what they call the Sherlock pipeline: a semi-automated system for extracting, classifying, and verifying glossary terms from heterogeneous source material. The numbers so far are modest but meaningful.2

02 — THE METHODOLOGY
THE SHERLOCK PIPELINE

The Sherlock pipeline is, at its core, a batch processing system. Source material — rulebooks, design documents, play transcripts, reference texts — is loaded into a queue. The pipeline passes each document through a series of Claude API calls: first to identify candidate terms, then to extract structured definitions, then to validate those definitions against a controlled schema. Human review is applied at the validation stage; the rest is automated.

The choice to use Claude as the extraction engine was deliberate. The team's hypothesis was that a reasoning model would produce higher-quality structured output from messy, heterogeneous sources than a classical NLP extraction pipeline. Early results appear to support this. The extracted entries carry richer semantic metadata than the team expected at this cost point — context notes, usage examples, cross-references to related terms — all generated in a single pass rather than requiring multiple refinement stages.3

The output format is a YAML term registry, stored in a version-controlled repository alongside the game rules it describes. Every term entry carries a status field: stub, draft, or approved. The registry is queryable at inference time: when Storyteller's AI encounters a term during a session, it can look it up and receive a structured definition rather than relying on the model's parametric memory.4

Methodology

Source ingestion. Raw documents are loaded into a YAML queue file (sherlock/queue.yaml). Each entry specifies the source file path, document type, expected term density, and processing priority. Queue entries are processed in priority order by the dispatcher CLI.

Extraction pass. The dispatcher calls the Claude API with a structured extraction prompt. The model is instructed to identify candidate terms and output a JSON array of objects conforming to the entry schema: term, definition, usage_notes, related_terms[], source_ref.

Validation pass. Extracted entries are checked against the existing registry to detect duplicates and conflicts. The pipeline flags ambiguous entries for human review. Clean entries are written to the term registry with status draft.

Approval. A human reviewer reads each draft entry, corrects errors, and promotes to approved. The registry is committed to version control. Downstream systems consume only approved entries at inference time.

03 — THE RESULTS
WHAT IT PROVES

Four completed batches representing 445 verified terms. That is not a large number in isolation — a standard dictionary runs to hundreds of thousands of entries. But the Open Adventure glossary is not a general-purpose dictionary. It is a controlled vocabulary for a specific rules system, and the team's contention is that 445 tightly-scoped, verified terms provide more reliable grounding for an AI game master than a model trained on the entirety of publicly available TTRPG material. Quality of signal, not quantity.5

The more significant result may be the process itself. At $0.13 per term in API costs, the pipeline is cheap enough that the team can afford to be aggressive about coverage. Every mechanic, every named character, every location, every piece of equipment can be indexed without meaningful budget constraint. The bottleneck is human review time, not compute cost.

This is a meaningful structural finding. Most AI content quality efforts focus on model-side improvements — fine-tuning, prompt engineering, model selection. Storyteller's bet is that the leverage is on the data side: that a smaller, cheaper model with excellent grounding data outperforms a more capable model with poor grounding data on domain-specific tasks. The pipeline exists to test that hypothesis in production.

"The bottleneck is human review time, not compute cost — and that is exactly the kind of bottleneck you want to have."

Storyteller's architecture separates the Play Engine — the real-time AI that runs sessions — from the Create Engine, which is used to build and maintain story content. The knowledge base sits beneath both. When the Play Engine needs to rule on a game mechanic, it queries the registry. When the Create Engine generates new narrative content, it does so with the same verified vocabulary available as a constraint.6

The claim is not that this eliminates AI error. It is that it makes errors tractable: detectable, attributable, and correctable at the data layer rather than requiring intervention in the model weights. A human editor can fix a wrong definition in the registry and have that fix propagate to all downstream AI behavior immediately. That is a fundamentally different maintenance model than fine-tuning.

04 — WHAT'S NEXT
THE ROADMAP

Storyteller's next phase is co-founder-led content development: moving from infrastructure to the narrative layer itself. The glossary pipeline continues in the background, processing the remaining queue of source documents. In parallel, the team is beginning work on the first Story Packages — discrete narrative scenarios built on the Open Adventure rules and designed to run through the Storyteller platform.

The engineering question looming over this phase is integration. The term registry exists. The story format — what the team calls TOME — is designed but not yet built. The Play Engine architecture is specified but not implemented. The next several months will determine whether the data infrastructure built to date connects cleanly to the product layer above it, or whether the specification-to-implementation gap produces the kind of technical debt that derails otherwise well-conceived systems.

For the moment, Storyteller is a knowledge base looking for an engine. The thesis — that you can build a reliable AI storyteller by solving the grounding problem first — remains unproven at scale. What is proven is that the grounding problem is solvable at reasonable cost, and that a small team can make meaningful progress on it in a short time. That is, for now, enough.
